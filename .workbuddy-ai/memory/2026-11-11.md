# 2026-11-11

## Smoother fleet-preparation drag (placement screen)

User reported the ship select / drag-and-drop on the fleet preparation screen
was not smooth.

Root causes found:
- `BoardCanvas` used competing vertical/horizontal `GestureDetector` drag
  recognizers inside a `ListView`: 18 px touch slop delayed the ghost and the
  scroll view could steal/cancel a vertical ship drag; `onDragCancel` even
  committed a stray placement.
- Every pointer move called `setState` on the whole `PlacementScreen`, plus
  one `addPostFrameCallback` per rebuild, repeated layout validation and a
  fresh `toPlacements()` list per getter access.
- Dropping the ghost cleared it before the Host echoed the layout, so the hull
  visibly snapped back to its old cell (LAN clients especially).
- Releasing outside the grid still placed the ship (PHASE3 §1.5 expects a
  cancel) because `onPreviewCleared` was never wired.

Changes:
- `lib/shared/widgets/board_canvas.dart`: StatefulWidget + `Listener`-level
  pointer handling; a conditional `EagerGestureRecognizer` claims the pointer
  at down only when a ship is selected / under the finger (empty-water touches
  still scroll the page); manual long-press timer keeps hold-and-swish rotate;
  callbacks deduped per cell; drop outside and pointer cancel never commit;
  `RepaintBoundary` and deep `shouldRepaint` comparisons.
- `lib/features/placement/presentation/placement_screen.dart`: preview cell is
  a `ValueNotifier` consumed by a `ValueListenableBuilder` around the board
  only; countdown timer moved into `_CountdownCard`; single guarded phase
  check; cached Host layout; optimistic `_pendingLayout` overlay until the Host
  answers (2 s fallback), Ready still gated on Host-confirmed ships.
- Tests: new `test/shared/widgets/board_canvas_test.dart` (5 gesture tests)
  and 3 new placement-screen tests.

Verification: `flutter analyze` clean; full `flutter test` 302/302 passing.
Note: in this environment `flutter test` needs
`NO_PROXY=localhost,127.0.0.1,::1 no_proxy=...` or the tester WebSocket
fails with "Invalid WebSocket upgrade request".
This drag work was committed as `fd84853`.

## Stale "The host closed the room." on the preparation screen

Second report: that alert text kept showing on the fleet-preparation page.

Root cause (session lifecycle, not a placement hint):
- `RoomSessionController.closeRoom()` used `copyWith`, so closing a room kept
  the old `snapshot` (still `status: placement`), `placement`, `countdown`,
  `notice` and `placementError`, and wrote the client-facing message into the
  **host's own** `errorMessage`. `RoomClosedEvent` did the same on clients.
- `reset()` existed but no screen called it, so `errorMessage` stayed forever;
  screens that render it unconditionally (bot setup, create room, lobby
  `_ClosedBanner`, snackbars) repeated it, and snackbars survive `context.go`
  in the root `ScaffoldMessenger`.
- `PlacementScreen` only checked `snapshot == null`, so it kept rendering a
  stale in-room board; `placementError` was never cleared, so its red hint
  stuck as well. No screen navigated Home on `RoomSessionStatus.closed`
  (PHASE7 §3.1 expects clients to return Home).

Changes:
- `room_session_controller.dart`: new `_closedRoomState()` builds a fresh
  terminal state (only status/code/message); host-initiated close no longer
  stores the client notice; `acknowledgeClosedRoom()` clears it after the
  one-time notice; placement streams clear `placementError` on an accepted
  layout; late client events after `closed` are ignored (watchdog race).
- `placement_screen.dart` / `lobby_screen.dart`: on `closed`, show the reason
  once in a SnackBar, acknowledge/reset state and go Home; no stale board.
- `bot_setup_screen.dart` / `create_room_screen.dart`: error text is gated on
  `status != closed`.
- Tests: new `test/features/rooms/domain/room_close_state_test.dart` (2) and
  a router-based placement test reproducing the stale closed state.

Verification: `flutter analyze` clean; full `flutter test` 305/305 passing.
This fix was committed as `9631ace`.

## Cannot go back to Home from Play vs Computer

Third report: the play-with-computer screen had no way back to Home.

Root cause: `HomeScreen` opened `/play-bot`, `/create-room` and `/join-room`
with `context.go(...)`, which **replaces** the GoRouter stack. With Home no
longer below the current page, `Navigator.canPop()` is false, the AppBar's
automatic back arrow is hidden, and the Android back gesture has nowhere to
go. None of those three screens had an explicit `leading` button (Lobby,
Placement and Host Settings do). Confirmed with two failing widget tests
(no `Icons.arrow_back`; `tester.binding.handlePopRoute()` did not reach Home).

Changes:
- `home_screen.dart`: those three launcher entries now use `context.push`,
  keeping Home in the stack so the system back gesture works.
- `bot_setup_screen.dart`, `create_room_screen.dart`, `join_room_screen.dart`:
  explicit AppBar back arrow calling `context.go('/')`, so the way Home is
  visible even when the stack was replaced (deep link / restored route).
- Test: new `test/features/bot/presentation/bot_setup_navigation_test.dart`
  (router-based, covers both the arrow and the system back).

Verification: `flutter analyze` clean; full `flutter test` 307/307 passing.
